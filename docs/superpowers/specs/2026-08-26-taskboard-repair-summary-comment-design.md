# Taskboard 修复总结评论设计

> 历史设计记录，非当前操作手册。下文的状态名、命令、实施步骤、测试结果及‘当前’均属于当时的设计或记录，不代表本版本已经实现或仍然适用。不要按其中的提交、测试优先或重启步骤直接执行；现行流程以 [README](../../../README.md)、[项目规则](../../../AGENTS.md) 和 [Skill](../../../skills/code-loop-board/SKILL.md) 为准。

## 目标

所有 Taskboard 修复会话在完成代码修复后，必须在任务详情中留下可供人工审批和后续追溯的结构化评论。评论需要明确记录分析过程、缺陷根因、修复内容、验证结果和剩余风险。

## 适用范围

- 自动认领的普通事项；
- 自动认领的 外部平台 缺陷事项；
- 没有自动化执行上下文、但由 Taskboard 提示词驱动的普通修复事项。

人工审批通过后的纯合并续跑不重复生成修复总结，只记录最终合并和推送结果。

## 执行路径

1. Codex 读取事项及全部评论并定位缺陷。
2. 按既有 TDD 要求完成 Red、最小修复和 Green 验证。
3. 自动 Worktree 任务完成本地 commit。
4. Codex 通过 `comment add` 写入一条结构化修复总结。
5. 评论写入成功后，自动 Worktree 任务才允许调用 `automation acquire-merge`，从而进入风险判断、人工审批或直接合并。
6. 非 Worktree 任务在评论成功后才允许流转到下一状态。

因此，命中门禁的任务进入 `pending_approval` 时，审批人已经可以在任务详情中看到完整修复依据。

## 评论格式

评论固定使用以下五个 Markdown 小节：

```markdown
## 分析过程
- 复现现象、排查路径和关键证据。

## 缺陷根因
- 明确造成缺陷的因果链，不能只重复表面现象。

## 修复内容
- 修改位置、行为变化和修复范围。

## 验证结果
- 实际执行的测试命令或验证用例；
- TDD 的 Red/Green 结果；
- 无法执行的验证及其具体原因。

## 剩余风险
- 已知风险和未覆盖范围；没有时明确写“无已知剩余风险”。
```

## 失败行为

结构化评论是进入审批、合并或下一状态的前置条件。`comment add` 失败时，本次执行不得继续调用 `automation acquire-merge`、不得推送，也不得流转任务；自动化任务按既有失败路径记录非敏感原因并释放槽位。

## 验收标准

- 自动 Worktree 任务进入待审批前，任务详情已有包含五个固定小节的修复总结；
- 未命中门禁而直接合并的任务，也在合并前留下同样的修复总结；
- 普通非 Worktree 修复任务在状态流转前留下同样的修复总结；
- 审批通过后的合并续跑不重复写修复分析；
- 评论失败时不会进入待审批、合并或后续状态。
