# 用 AI 初始化缺陷拉取与部署定时任务

## 先复制这段提示词

在 Codex 中打开看板仓库，复制下面的提示词。AI 会先读已有配置，再逐步提问，不要求用户先填写整张技术表。

```text
请使用 $code-loop-board，按 scheduled-integrations 引导，为我初始化缺陷拉取和部署两个定时任务。
请先读取现有项目与配置，以提问方式收集信息，每轮只问一个主题，不一次甩给我长表。
先问我的缺陷列表来源地址和部署地址，再问范围、环境、仓库/分支、周期、时区和验证范围。
每次获得答案就保存到本机 schedule-config.json；已有值先展示非敏感摘要，只问缺失或变更项。
缺配置文件时从 docs/integrations/schedule-config.example.json 生成骨架，不覆盖已有值。
页面确认优先使用可用的 Playwright；没有才用浏览器控制插件；两者都没有才用 computer use。
这是可用性优先级，不挨个使用，也不因登录或页面操作失败自动切换工具。
根据真实观察生成并验证保存的脚本，再通过实际可用的调度器创建或更新两项计划。
未具备独立运行条件的计划保持暂停；没有调度工具时保存提示词并说明手动创建位置，
不要声称已经创建。跑完按本指南做闭环验证，从真实来源/部署运行回读到看板结果，
并检查调度器实际执行记录；只有计划登记或脚本单独成功不能算链路跑通。
最后给出配置路径、计划 ID、闭环结果、待完成项以及后续修改方法。
不要提交或推送 Git，不要把真实地址、账号、Cookie 或 token 写入公开材料。
```

本指南用于指导使用者在自己的环境中生成计划，不会在阅读或安装 Skill 时创建任务。用户只要求检查或更新文档时，不操作调度器。

## 一、确认项目与输入

1. 查询已有看板项目，读取实际 ID。嵌入模式下没有记录时，引导用户在看板选择 Codex 自动识别的项目，再查询；不重复创建。调度器项目 ID 与看板项目 ID 分别查询，不假定相同。
2. 导出项目生效的看板 JSON，确认 `automation.bindings` 和 `manualTransitions`。发布需要的 `releaseReady`、`releasing`、`review` 是语义角色，实际列 ID 从 JSON 获取；缺失时列出待配置项。不要硬编码平台状态或根据中文列名猜测。
3. 核对用户粘贴的缺陷列表和部署地址分别指向哪个项目、环境及筛选范围。缺地址就请用户粘贴地址；部署首页若不足以确定流水线，继续确认具体流水线。地址不含密码、token 等秘密；认证由用户在本机完成。
4. 明确周期、时区和批量条件。不要继承参考任务的团队名称、固定分钟数、阈值、前后端目录或模型设置。缺信息时继续完成独立部分，不能替用户开启未确定的部署。

### 逐步提问并保存答案

先读取现有文件。首次使用从看板仓库的 `docs/integrations/schedule-config.example.json` 生成 `.loop-integrations/<实际项目ID>/schedule-config.json`，保存确认的实际项目 ID 后再逐项补充。不要在公开模板中填写用户的答案。每轮只问下面一个主题，等待回答后立即写入对应字段，并简短说明保存位置；能从现有项目/配置读取的事实先核对，不重复询问。

| 顺序 | AI 向使用者提的问题 | 保存字段 |
| --- | --- | --- |
| 1 | “为当前项目配置吗？运行方式是本地网页、嵌入 Codex，还是云端协作？两项计划都需要吗？” | `project`、`setup.runMode`、两项 `enabled`（未验证前保持 false，启用意图记录在 `setup.requestedJobs`） |
| 2 | “请粘贴需要拉取的缺陷列表地址。” | `issueSync.listUrl` |
| 3 | “请粘贴要操作的部署或流水线地址，目标环境是什么？” | `deployment.url`、`deployment.environment` |
| 4 | “缺陷需要按版本、负责人或哪些条件筛选？是否需要同步评论、图片及已导入事项的关闭/重开？” | `issueSync.filter`、`issueSync.content`、`issueSync.trackImportedIssues`、`issueSync.closeOnSourceClosed` |
| 5 | “要发布哪些仓库、哪些分支？有待发布任务就部署，还是达到数量或等待时间后再部署？” | `deployment.repositories`、`deployment.batch`；仓库/分支先实际识别再请用户确认 |
| 6 | “缺陷拉取和部署检查各多久运行一次？使用哪个时区？” | `issueSync.schedule`、`deployment.schedule` |
| 7 | “请在本机完成登录。哪条缺陷可以用于验证？允许在哪个环境、哪个版本验证部署，还是先只读？” | 两项 `authRef` 及 `verification`；只保存本机认证引用，不询问密码或 Cookie |

需要部署时追加询问：“部署成功后是否回写源事项为待验证？失败后是否允许在有新提交时创建下一批？”答案写入 `deployment.requestVerification` 和 `deployment.retryOnNewCommit`；平台实际状态由适配器映射，不把问话中的名称用作状态 ID。

这些问题按依赖逐步进行，不能把未回答视为同意。缺少模块、认证文件或运行依赖时，说明具体路径、取得方式及填写/安装方法，继续完成不依赖它的部分。来源范围 ID、连接 ID、Node/runner 路径和调度器项目 ID 由 AI 实际核对后写入，不能要求用户猜技术标识。

模板字段为 null 表示待确认，空数组/空对象也不自动表示“不限制”或“无需仓库”。`setup.requestedJobs` 记录用户要配置的任务类型，`enabled` 记录实际已启用状态；只有用户要求启用、运行条件已验证且调度器回读为启用时才改为 true。生成脚本时必须实现模板中实际使用字段的读取，不能留下只写不读的配置。

缺陷连接仍由核心读取 `integrations.json`。生成 `run-sync.mjs` 时每轮读取 schedule-config，将 listUrl（存入适配器约定的连接 options）、scopeId、filter、closeOnSourceClosed 和 delivery 映射到选定连接及项目映射，再调用 integration sync；仅更新匹配条目，保留其他连接、认证和发布配置，避免整份覆盖。同步配置后调用既有 CLI，不能把这些新字段直接当成核心已支持的参数。需要详情跟踪或图片迁移时，在生成的 runner/适配器中实现并验证，未完成则列为缺口。

### 配置值和修改含义

- `setup.runMode` 使用 local、embedded 或 cloud；`requestedJobs` 从 issueSync、deployment 中选择。未选择的任务不创建。
- 两项 `schedule.intervalMinutes` 是用户确认的正整数分钟数，`timezone` 是确认的时区名称。`appliedSchedule` 保存调度器回读后的周期与时区，未登记时为 null。
- `deployment.batch.mode` 为 immediate 或 threshold。immediate 表示有合格任务就发布；threshold 表示数量达到 `minCount` **或**最长等待达到 `maxWaitMinutes` 就发布。两种阈值可以只启用一种，未启用的值为 null，但 threshold 不能两项都空；比较统一使用“大于等于”。
- 仓库项使用 `{ repositoryId, targetBranch }`，与现有 delivery 契约一致。需要缺陷进入发布流程时，确认 `issueSync.delivery.mode=release` 并填入其 repositories；这些交付快照只用于新导入事项，不覆盖已有任务的仓库快照。部署筛选用 `deployment.repositories`，变更它不会重写已导入任务。
- `issueSync.filter` 和 `deployment.parameters` 的键来自实际适配器，逐项说明并保存；不要编造通用平台字段。`authRef` 是本机文件/环境变量引用；浏览器登录状态的保存方式写进 ADAPTER.md。
- `verification.deploymentMode` 使用 readOnly 或 trigger，`deploymentVersion` 保存允许验证的版本；verified 字段只在真实脚本验证后更新。`runtime`、runnerPath、statePath 使用实际绝对路径，避免定时任务工作目录不同导致找不到脚本。

## 二、选择一种可用的页面确认工具

| 优先级 | 选择条件 | 用途 |
| --- | --- | --- |
| 1. Playwright | 当前有可调用的 Playwright 工具或可运行的本机 Playwright 环境 | 观察真实页面、frame、定位器和导航结果，验证可保存的脚本 |
| 2. 浏览器控制插件 | 当前没有可用的 Playwright，但有浏览器控制插件 | 用可用浏览器会话确认页面结构、交互和结果，记录足以编写脚本的事实 |
| 3. computer use | 前两者都不可用，且当前提供 computer use | 通过可见页面确认流程；只能看到像素时不能编造 DOM 选择器 |

这是**可用性优先级**，不是顺序执行或错误重试链。选定工具后，登录失效、验证码、权限不足、页面变化应在该路径查明；更换工具不能绕过访问限制。三种工具都没有时，说明需要哪种工具或环境，保留待完成项。

探索阶段可以用浏览器插件或 computer use，但最终脚本必须在未来定时任务的实际运行环境中验证。若该环境还没有 Playwright，说明依赖、浏览器及登录态的准备方法，按用户授权准备；准备完成前只记录脚本草稿，不把人工可点通称为无人值守可运行。调用工具前读取其实际文档，不编造浏览器插件 API。

缺陷页面需确认列表筛选、分页、稳定事项 ID、真实详情 URL、正文及评论；需要附件时单独确认下载和本地上传路径。部署页面需确认目标环境、分支/版本参数、触发入口、确认操作、新构建 ID/URL 及结果读取方式。选择器、frame 名称和源状态映射均来自本次观察，不复制其他平台的选择器。

## 三、保存两个适配入口

先从固定 runner 或用户工作区定位看板仓库。以下路径相对看板仓库根目录；安装后的 Skill 目录不是看板仓库。只补缺失文件，不覆盖已有配置。

| 产物 | 如何生成及使用 |
| --- | --- |
| `integrations.json` | 按仓库连接示例注册缺陷 provider；部署另外注册 `releaseProviders`、`releaseConnections`，不混用两种连接 |
| `integrations/local/<issue-provider>/provider.mjs`、`ADAPTER.md` | 从仓库 Playwright 模板实现缺陷契约；记录真实列表/详情读取、状态映射及验证结果 |
| `integrations/local/<issue-provider>/run-sync.mjs` | AI 生成的本机同步 runner；读取计划配置，更新对应连接映射后调用 integration sync，实现用户选择的补充同步能力 |
| `integrations/local/<release-provider>/provider.mjs`、`ADAPTER.md` | 根据目标部署页面实现 `triggerRelease(context, input)` 和 `getRelease(context, input)`，记录参数与认证引用 |
| `integrations/local/<release-provider>/run-release.mjs` | AI 生成的本机发布 runner；负责候选任务、批次、调用发布适配器、查询结果及看板回写 |
| `.loop-integrations/<project-id>/schedule-config.json` | 从 `docs/integrations/schedule-config.example.json` 生成，AI 与 runner 约定的私有配置，保存两个地址、项目及连接 ID、仓库/分支/环境、周期、时区、批量条件和固定脚本路径 |
| `.loop-integrations/<project-id>/release-state.json` | 发布 runner 维护批次成员、提交快照、触发尝试、构建 ID/URL 和结果，供下一轮恢复 |
| `.loop-integrations/<project-id>/schedules.md` | 保存最终两份任务提示词、计划 ID、运行环境、配置/脚本位置和实际验证记录，不保存秘密 |

`schedule-config.json`、`release-state.json` 是初始化时生成的本机 runner 文件约定，**不是核心已内置且自动读取的配置**。AI 必须同时实现对应读取/写入逻辑并说明字段。真实地址只保存在这些被忽略的本机配置中，计划提示词引用路径；公开文档不粘贴生成后的私有内容。

缺陷拉取已有入口：`clb integration sync --connection CONNECTION_ID --project PROJECT_ID --json`。没有全局 clb 时使用实际 Node 路径和 `<看板仓库>/cli/clb.mjs`，按参数数组运行。写操作使用当前执行会话的 `CODEX_THREAD_ID` 或 `--thread-id`，不得保存初始化会话 ID 供以后冒用。

部署目前只有 `server/integrations/releases.mjs`，没有内置发布 CLI/HTTP 入口。生成的 `run-release.mjs` 应使用 `createReleaseService({ configPath })`，调用 `triggerRelease({ connectionId, ...input })` / `getRelease({ connectionId, ...input })`；服务传给适配器的 context 是 `{ connection, root }`。两者返回 `{ id, url, status }`，status 为 queued、running、succeeded、failed 或 canceled。传入参数由实际适配器约定；触发必须返回本次新构建，不能返回列表中的旧构建。不要在提示词里发明 `clb release` 命令。

## 四、先实际跑通，再登记计划

缺陷同步：检查声明能力，读取授权样例，执行一次同步，再通过任务 API/CLI 回读，确认项目、结构化 `externalIssue`、状态、正文和评论。检查返回的 `created/updated/skipped`，不是只看进程退出码。现有 sync 只处理 `listIssues` 返回的事项；若用户需要持续跟踪已导入事项的关闭和重开，适配器/runner 还需明确实现这些事项的详情读取，不能假设核心会自动扫描全部详情。附件也不是现有 sync 自动迁移的能力，未实现时明确列出。

部署：先验证登录及只读查询，再在用户授权的环境/版本触发样例，取得新构建 ID，查询该次运行的实际结果并回读相关任务。用户仅允许只读或未提供测试环境时，不实际触发，发布能力标记未验证，生成的部署计划保持暂停。不能把 `prepare-release`、源事项的 fixed 或按钮点击成功解释为部署成功。

部署 runner 至少按这个顺序执行：

1. 读取当前配置、看板 JSON 和上次批次。已有构建先查它的结果；每轮有运行中的批次时不再触发同一范围的新构建。
2. 从目标项目筛选 `delivery.mode=release`、绑定的待发布状态、仓库/分支/环境匹配且代码交付已结束的任务。按实际仓库列表取提交快照，不要求固定前后端两个仓库，不切换母仓库分支；普通任务和其他分支不混入该批。
3. 按用户配置的数量或等待时间判断；等待时长使用进入待发布状态的时间，不能用任意修改时间替代。先验证部署入口可用，再冻结本批任务与提交快照；后来进入的任务留给下一批。
4. 按项目允许流转更新为发布中。每次写入重读任务、使用最新版本和本轮会话身份。未结束的自动化执行先走其受控流程，不能通过普通移列绕过。
5. 在触发前持久化本批的尝试记录，触发后立即保存新构建 ID/URL。已有尝试但没有明确构建 ID 时先核实，不盲目再点；已有 ID 时只查询该构建。此记录须由 runner 实现，不依赖 AI 对话记忆。
6. 成功后，对仍属于本批的任务调用已验证的 `request_verification` 外部动作（有来源且项目要求时），确认 `ok/verified/localCompleted` 及适配器约定的目标语义，再按 JSON 流转到 review。无外部来源时跳过源写回；已经终结或退出本批的任务不回退。
7. 运行中或超时保存进度供下一轮继续查。失败/取消记录结果；相同提交不循环触发，只有用户配置允许且提交变化时才建立新批次。源写回失败与部署失败分开记录，不能因为回写失败再部署一次。

上述步骤是要生成并验证的 runner 行为，不是当前发布服务模块已经完成的能力。

## 五、生成两份定时任务提示词并创建或更新

在用户要求初始化两个定时任务时，使用当前环境实际提供的调度工具，先查询同项目同用途计划。分别建立“<项目名> 缺陷拉取”和“<项目名> 缺陷批量部署”；存在则按用户指定范围更新，保存真实计划 ID。保持两项独立，不把它们放进自动修复槽位或合成一个任务。

使用 Codex 提供的自动化工具时遵循其当前参数与计划类型要求；需要项目 ID 时先查询项目，不把看板 ID 当成调度器项目 ID。其他调度器也必须具有可用的 AI 执行环境。不要只写 automation.toml 或在磁盘保存提示词就声称任务已登记。

生成提示词前，把下面的路径/ID占位符替换为已核实的本机值，真实 URL 留在私有配置里。周期和时区以调度器字段为准，与配置记录一致；不把“每小时”同时硬编码在正文里造成日后冲突。

**缺陷拉取任务正文：**

```text
使用 $code-loop-board。读取 <私有配置绝对路径> 和 <缺陷适配记录绝对路径>。
目标看板项目为 <实际看板项目ID>，使用配置中的连接、来源范围和筛选条件。
通过 <实际Node路径> 调用 <已验证run-sync.mjs绝对路径>，按其参数契约传入配置位置
和本轮会话身份；runner 每轮读取配置并经固定 clb 入口执行 integration sync，
显式传入 connection 和 project，不依赖 context current 猜项目。
复用已验证脚本与本机认证，不重新探索页面，不临时生成选择器。
检查 created/updated/skipped 并回读实际导入结果；部分失败不报告整批成功。
只汇报新增、更新、跳过、失败和待处理事项，不输出凭据或完整私有配置。
认证或页面结构变化时记录失败步骤，按适配记录维护后再运行，不把登录失败当空列表。
```

**缺陷批量部署任务正文：**

```text
使用 $code-loop-board。读取 <私有配置绝对路径> 和 <发布适配记录绝对路径>。
通过 <实际Node路径> 调用 <已验证run-release.mjs绝对路径>，
使用已验证的参数契约传入配置位置及本轮会话身份。
按 runner 的持久批次记录恢复已有构建；没有活动批次且满足配置的发布条件才触发。
严格使用已冻结的任务、环境、仓库、分支和提交；不切换母仓库，不重复触发同一批次。
以精确构建 ID 的实际结果判定成功，并分别确认源状态回写与看板流转结果。
运行中、失败、回写失败分别记录；未经确认不能把任务标为已部署或回归完成。
汇报批次、构建结果、成功/跳过/失败数量和需要用户处理的项；不输出认证信息。
```

缺少调度工具时，将两份最终提示词及周期/时区保存在本机 `schedules.md`，明确“尚未创建”，引导用户到所用 AI 工具的定时任务入口分别粘贴。缺少环境、认证或验证时保存暂停计划；未解决前不启用。无人值守运行必须能访问本机服务、脚本、网络和认证，不能只在初始化交互浏览器中可用。

最后回读两项计划的 ID、项目、正文、周期、时区和状态，确认指向正确的固定 runner。分别报告“文件已生成”“脚本已验证”“计划已创建/更新”“是否启用”，附具体待配置路径和下一步。已有真实部署样例无需重复触发，只核对计划配置与已验证入口一致。

## 六、闭环验收：跑完必须确认链路通了

分别检查“脚本单次验证”和“定时任务实际执行”。使用用户已授权的样例与部署环境；已有同一次构建时继续查询，不为了验收再触发一遍发布。没有真实访问条件、发布授权或调度运行记录时，如实标记待验证，不用模拟结果替代。

### 缺陷拉取闭环

1. 记录授权源事项的稳定 ID 和当前真实字段，确保它符合配置中的来源范围。
2. 通过保存的 run-sync 入口执行，回读本地事项的 projectId、externalIssue、状态绑定，以及用户要求同步的正文/评论/图片；有图片时检查本地附件可访问。
3. 在看板打开这条实际事项，确认用户能看到同步结果。若本次没有新增/更新，只能证明空轮询能运行；用已授权且符合条件的样例验证导入或更新，不能把零事项报告当作完整成功。
4. 再执行一次读取同步，确认同一 externalIssue 没有重复创建任务，同一源评论没有重复追加。需要关闭/重开跟踪时，用允许的样例验证对应回读与流转，不擅自修改源事项制造样例。

### 部署闭环

1. 确认一批授权范围内的待发布任务及其仓库、分支、提交、环境，读取保存的批次记录。
2. 经 run-release 入口确认本次新构建 ID/URL，继续查询这一构建直到得到真实终态；仅 queued/running 不算部署成功。
3. 构建成功后逐项核对：要求源回写的任务在来源系统已达到适配器约定目标；本地对应任务按 JSON 进入 review；无需源回写的项目明确记为“不适用”。这些结果都实际回读，不能只看 runner 的成功文本。
4. 在看板查看任务状态和交付记录，再执行一次发布检查，确认它恢复/读取已完成批次，没有给相同批次和提交再次触发构建。构建失败、仍在运行或任一回写失败时，记录链路停在哪一步，不能标记整条通过。

### 调度器闭环与交付

通过调度器提供的实际“立即运行/运行一次”入口验证两项计划；如果没有该能力，等待首次计划执行并读取其记录。不能手写一个假运行 ID，也不能把终端手动调用冒充定时任务执行。部署的这一轮优先查询已验证批次，核对没有重复触发，避免重复发布。

核对运行记录中的计划 ID、实际项目、固定 runner、配置位置、运行结果，与上述两条回读链路对应。调度运行访问不到脚本、服务或登录态时，修复明确的失败点后再执行该路径；未解决就暂停该项并记录待用户完成的步骤。

在私有配置的 `verification.chains.issueSync` / `deployment` 保存 `passed`、`lastRunId`、`verifiedAt`、`evidencePath`。只有对应链路的实际数据回读和真实调度运行均通过，passed 才为 true；尚未调度时保持 false。run ID 使用调度器实际标识；调度器不提供 ID 时保持 null，在 evidencePath 指向的记录中保存可核对的计划 ID、执行时间及结果，不能自行伪造。

最终逐条报告：输入样例 → 实际脚本 → 计划及运行记录 → 看板/构建/源状态结果 → 通过或待验证。证据留在被忽略的本机目录，公开交付只描述能力与未完成项。

## 七、以后怎样修改

- 改地址、筛选条件、部署环境、批量条件：编辑本机 `schedule-config.json`，或让 AI 提问后修改。runner 每轮重新读取；新地址若指向不同平台/页面结构，先更新适配器并验证，不沿用旧选择器冒充已接通。
- 改周期、时区、启用状态：让 AI 更新 JSON 后，按 `automationId` 修改对应调度器计划并回读。只改 JSON 不会改变调度器的触发时间；未成功更新时保留旧的 `appliedSchedule`，报告两者尚未一致。
- 改连接映射或认证引用：同步检查 `integrations.json` 和 ADAPTER.md；凭据内容仍由用户在本机管理。缺陷 runner 只更新自己负责的映射，不覆盖其他项目。
- 改脚本路径或项目绑定：同时更新配置和实际计划正文/项目字段并回读；正文中的固定入口不会随 JSON 自动迁移。

计划创建/更新回读成功后，将真实 `automationId`、`appliedSchedule`、`enabled` 写回对应项，并在 schedules.md 保留验证摘要。若没有可用调度器，这些登记字段保持未完成，不能填虚构 ID。
